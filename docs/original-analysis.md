# 《宿命篇》原版分析与《天问篇》开发顺序

- 已逐文件核对 RAR 与提供的解压目录一致，共 1,176 个文件，含数据库、地图树和 291 个地图文件；现已完成数据库、地图和事件的[首轮静态索引](../research/suming/README.md)，尚未运行原游戏。
- 样本开场声明自述 RM2003 v1.09a；运行时 PE 资源版本为 1.0.9.1。[首轮逆向记录](reverse-engineering.md)列出证据与待验证项，后续仍需运行验证。
- 收到样本前的[联网来源核查](source-retrieval-2026-11-10.md)保留为历史记录；《天问篇》正文获取状态见[剧本来源记录](tianwen/README.md)。

## 1. 先固定原版样本

拿到压缩包后，记录来源 URL 或提供方式、获取日期、文件大小、SHA-256 和包内版本说明；解压后保留原件，使用副本分析。不同版本分别建档，避免把补丁版、整合版或其他同名游戏的数据混在一起。

首先查找以下文件；文件名与格式是识别线索，不能单独证明游戏身份或精确引擎版本：

| 文件 | 首轮分析目的 |
| --- | --- |
| `RPG_RT.ldb` | 数据库：角色、技能、物品、敌人、战斗编组、公共事件及开关/变量定义 |
| `RPG_RT.lmt` | 地图树、地图关系与起始位置 |
| `Map*.lmu` | 地图图块、地图事件、事件页条件与命令 |
| `RPG_RT.ini`、`RPG_RT.exe`、DLL 或补丁文件 | 配置、运行时版本和扩展依赖线索 |
| `Save*.lsd` | 若有存档，用于比较特定剧情前后的状态变化 |

如果没有这组数据，先重新识别封装方式和引擎；不要预设一定是 RM2003。不要因为拿到了可执行文件，就把它当作编辑器工程或原始源码。

## 2. 先解析数据与事件

[EasyRPG/liblcf](https://github.com/EasyRPG/liblcf) 支持 RPG Maker 2000/2003 的数据格式；官方提供 LCF2XML（数据与 XML 转换）和 LCFSTRINGS（字符串提取）。[工具下载页](https://easyrpg.org/tools/downloads/)列出了可用构建；使用时记录具体版本或构建标识。

1. 在工作副本上选择数据库、地图树和一张地图做试转换，保存输入哈希、工具版本、调用参数、编码设置与转换日志。
2. 用游戏中可见的中文名称检查编码；乱码时保留原始字节并调整编码设置，不覆盖原文件。
3. 试转换成功后再批量处理；记录失败文件和未识别字段，不把“工具输出成功”当作解析完整。
4. 为记录保留原始 ID。地图事件定位到“地图 ID / 事件 ID / 事件页 / 命令序号”；公共事件与战斗事件记录对应所属 ID 和命令序号。
5. 对话、公共事件、条件分支、开关/变量读写、道具授予和地图跳转一起分析。仅抽出台词无法还原游戏流程。
6. 完整原版目录已按用户要求归档；在工作副本上分析与导出，仓库保存工具使用说明、结构索引、规则摘要与核验记录。

优先产出：

| 产出 | 需要回答的问题 |
| --- | --- |
| 样本清单 | 正在分析哪个版本？数据是否齐全？ |
| 数据库与地图索引 | 哪些 ID 对应角色、物品、敌人和地点？ |
| 事件与状态依赖表 | 哪个事件在什么条件下触发，修改哪些开关和变量？ |
| 主线、支线、结局流程图 | 分支条件是什么，哪些事件会使任务失效？ |
| 资源引用清单 | 地图、事件和技能引用哪些图片、音乐或运行时扩展？ |

初期优先确认“开场 → 地图跳转 → 一场战斗 → 一个剧情分支 → 保存与读档”这条小流程，再扩展到主线和隐藏结局。

## 3. 用运行结果核对规则

对静态分析发现的条件，记录可重复操作的验证步骤。每条结论区分“网页线索”“静态数据证据”“运行验证”；未知项保持未知。

- 在原版中完成小流程，对照事件命令与实际表现。
- 比较分支前后的存档，核对开关、变量、队伍与道具变化。
- 优先验证续作会用到的结局状态、角色存亡、物品含义及核心战斗规则。
- 对补丁、DLL 或非标准事件单独记录。只有常规数据解析不能解释行为时，再定位相关运行时代码。
- 使用兼容运行器时，将其表现与原运行时区分记录，避免把兼容性差异当作原作规则。

验证记录至少包含：样本哈希、事件位置、预置状态、操作、预期与实测结果、截图或存档的本地索引。

## 4. 再设计《天问篇》的可玩结构

剧本整理可以与原版解析并行。先完成上述小流程和续作衔接点核验，再确定续作的实现方案；不要求先完整复刻原作全部内容。

1. 根据实际剧本核对章节完整性、人物、地点、场景与叙事顺序。
2. 明确承接《宿命篇》的哪个结局；列出角色状态、关系、物品和世界状态，标注证据与待决项。
3. 将剧本拆成“场景目标 / 可操作角色 / 探索或战斗 / 选择 / 状态变化 / 下一场景”。
4. 区分原版规则、续作剧本明确要求和新设计提案；新设定不能冒充作者原稿。
5. 将已核验的规则映射到 UE 数据与系统，先做一个可玩的场景，验证对话、任务、战斗、地图切换与存档，再扩展章节。

## 下一步分析目标

数据库、地图树和全部地图的首轮静态索引已经完成；下一步在原运行时验证开场和结局分支，并逐一追踪支线变量的写入。并行沿原作者帖子寻找《天问篇》可核验正文。当前不能据网页梗概填造事件 ID、数值、完整台词或续作章节。
